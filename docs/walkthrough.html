Code walkthrough: the Energy Brief Harness Agent

A guided tour of this repo for people new to the Microsoft Agent Framework Harness agent. We build one agent, run it on a laptop, then ship the same code as a Foundry Hosted Agent that pulls its Skills from the Foundry project.

What the agent does

"Brent" is an oil and gas market analyst. It pulls delayed futures prices (WTI, Brent, Henry Hub, RBOB, heating oil) and public energy headlines, then writes a one-page Markdown market brief.

What you will learn

  • What create_harness_agent gives you, and when to use something lower-level
  • How Skills (SKILL.md plus scripts) load on demand
  • The "one factory, two entry points" pattern for local and hosted runs
  • How to publish skills to Foundry and deploy a hosted agent with azd
Preview
Hosted Agents, the Foundry skills API (project.beta.skills) and the Harness packages are preview features. Names and signatures in this guide match the versions pinned in src/energy-brief-agent/requirements.txt (for example agent-framework-core 1.14, agent-framework-foundry-hosting 1.0.0b260813) and may change.

What is the Harness agent?

A model on its own answers one prompt. An agent wraps a model with a loop that can call tools, keep conversation state and decide what to do next. A harness goes further: it adds the scaffolding an agent needs to work through long, multi-step tasks without you assembling each piece.

In Agent Framework (Python), the harness is a single factory function:

from agent_framework import create_harness_agent
from agent_framework.foundry import FoundryChatClient
from azure.identity import AzureCliCredential

agent = create_harness_agent(
    FoundryChatClient(project_endpoint=..., model="gpt-5.4-mini", credential=AzureCliCredential()),
    agent_instructions="You are a helpful energy analyst.",
)
session = agent.create_session()
print(await agent.run("Plan a market brief for today.", session=session))

An important detail: create_harness_agent returns an ordinary agent_framework.Agent. The harness is a preconfigured Agent, not a separate runtime. Anything that accepts an Agent (hosting servers, workflows, middleware) accepts a harness agent too. That is how this repo hands the same object to ResponsesHostServer in the hosted container.

Opt-in extras include Skills (skills_provider or skills_paths), shared file access, background sub-agents, a shell executor and bounded looping (loop_should_continue). This repo opts in to Skills and opts out of several defaults. We will see why.

Harness vs the lower-level options

Agent Framework gives you a ladder. Each rung adds behavior on top of the one below it.

1. Chat client · FoundryChatClient(...).get_response(messages)
One model call. You own the tool loop, history and prompts.
2. Agent · Agent(client, instructions, tools=..., context_providers=..., middleware=...)
Tool-calling loop, sessions and streaming. You choose every provider and option.
3. Harness agent · create_harness_agent(client, ...)
An Agent pre-wired with todos, modes, compaction, file memory, web search, approvals and optional Skills.
Alternative: service-defined agent · FoundryAgent(project_endpoint, agent_name=...)
Connects to an agent whose definition lives in Foundry (a Prompt Agent or a Hosted Agent). The service owns the definition.

The same agent at each level

Pros and cons of the Harness agent

Pros

  • Batteries included. Planning, todos, compaction, memory and approvals in one call, with defaults tuned for long tasks.
  • Still a plain Agent. Works with streaming, sessions, middleware, workflows and ResponsesHostServer unchanged.
  • Easy opt-outs. Every default has a disable_* flag or a replaceable provider, so you can trim it down.
  • Skills are first-class. One skills_provider argument gives progressive disclosure of domain know-how.
  • Model-agnostic. Wraps any chat client (Foundry, Azure OpenAI, OpenAI, Anthropic and others).
  • Fast to demo. Demo 1 is a working multi-turn agent in about 15 lines.

Cons

  • Preview. APIs and default behavior can change between releases.
  • More implicit behavior. Hidden harness instructions and extra tools make it harder to see why the model did something.
  • Higher cost and latency. Extra tool schemas and instructions go out on every call. That is overkill for a one-shot classification.
  • Defaults assume a stateful, interactive host. File memory and modes need turning off in a stateless container. This repo does that.
  • Built-ins can compete with your tools. Web search competes with skill scripts and adds citation markers, so this repo disables it.
  • Auto-approval is a security decision. Fine for read-only demos. Revisit it for tools with side effects.
Rule of thumb
Start with the harness when the task is open-ended or multi-step and you want results quickly. Drop to Agent when you need precise control over prompts, tools and cost, or when the task is narrow. Use FoundryAgent when you are consuming an agent that is already defined in Foundry rather than building one.

Architecture

The key design choice: one agent factory, two entry points. The local demos and the hosted container both call build_energy_agent(). Only a hosted=True flag changes behavior, so a local run is a faithful test of what you deploy.

Both demos import a small helper module. It does three jobs.

1. Make the agent package importable and load config

2. Build the chat client

demos/_common.pydef make_client():
    from agent_framework.foundry import FoundryChatClient
    from azure.identity import AzureCliCredential

    missing = [k for k in ("FOUNDRY_PROJECT_ENDPOINT", "AZURE_AI_MODEL_DEPLOYMENT_NAME") if not os.getenv(k)]
    if missing:
        sys.exit(f"Missing {', '.join(missing)} in .env - run `make infra` first.")
    return FoundryChatClient(

        model=os.environ["AZURE_AI_MODEL_DEPLOYMENT_NAME"],
        credential=AzureCliCredential(),
    )

Locally we authenticate with AzureCliCredential, so no keys are involved. The hosted version swaps this for a managed identity.

3. Stream a turn and show tool calls inline

demos/_common.pyasync def stream_turn(agent, message: str, session) -> str:
    chunks: list[str] = []
    seen_calls: set[str] = set()
    async for update in agent.run(message, session=session, stream=True):
        for content in update.contents or []:
            ctype = getattr(content, "type", "")
            if ctype == "function_call":
                call_id = getattr(content, "call_id", None) or id(content)
                if call_id in seen_calls or not getattr(content, "name", None):
                    continue
                seen_calls.add(call_id)
                print(f"\n  ⚙ {_describe_call(content)}", flush=True)
            elif ctype == "text" and content.text:
                chunks.append(content.text)
                print(content.text, end="", flush=True)
    print()
    return "".join(chunks)
Teaching point
agent.run(..., stream=True) yields updates whose contents mix text and function_call items. Printing the function calls (⚙ load_skill(energy-market-brief), ⚙ run_skill_script(energy-market-brief/fetch_prices.py)) makes the agent's reasoning visible on stage. Streaming can repeat a call as its arguments arrive, so the code de-duplicates by call_id.

Instructions: persona plus grounding rules

You are "Brent", an energy-markets analyst copilot for Forward Deployed Engineers
working with oil & gas customers. Today is {date.today():%A %d %B %Y}.

The factory and its knobs

energy_agent.pydef build_energy_agent(client, *, skills_dir=LOCAL_SKILLS_DIR, hosted=False, **overrides):
    kwargs = {
        "name": "energy-brief-agent",
        "description": "Oil & gas market analyst that writes daily market briefs.",
        "agent_instructions": ANALYST_INSTRUCTIONS,
        # Foundry stores conversation state server-side, so don't replay history locally.
        "history_provider": InMemoryHistoryProvider(load_messages=False),
        # Skills are the source of truth; web search competes with them.
        "disable_web_search": True,
        "max_context_window_tokens": 128_000,
        "max_output_tokens": 16_000,
    }
    if skills_dir is not None:
        kwargs["skills_provider"] = build_skills_provider(skills_dir)
    if hosted:
        # Platform owns history; container filesystem is ephemeral -> stay stateless.
        kwargs.update(
            disable_file_memory=True,
            disable_mode=True,
            default_options={"store": False},
        )
    kwargs.update(overrides)
    return create_harness_agent(client, **kwargs)
SettingWhy
disable_web_search=TrueKeeps data retrieval in the skill scripts so every number is traceable to tool output. It also avoids citation tokens in the saved brief.
InMemoryHistoryProvider(load_messages=False)The Foundry Responses API keeps conversation state. Replaying it locally would duplicate messages.
hosted=True → disable_file_memory, disable_mode, store: FalseIn a container, a reused process must not leak one request's notes or mode into the next. This is the "cons" list from earlier in practice.
**overridesCallers can tweak any harness option, for example Demo 2 passes disable_file_memory=True.

Skills skills/<name>/SKILL.md + scripts/

A skill is a folder with a SKILL.md (YAML front matter plus Markdown instructions) and optional scripts. Skills use progressive disclosure:

  1. At startup the model sees only each skill's name and description.
  2. When a request matches a description, the model calls load_skill to read the full body.
  3. The body tells it which script to run, and the model calls run_skill_script through the script runner.

That keeps the context small until a skill is needed, which is why the description is the routing signal and the most important line in the file.

skills/energy-market-brief/SKILL.md---
name: energy-market-brief
description: Produce a concise oil and gas market brief (WTI, Brent, Henry Hub, products, Brent-WTI spread, 3-2-1 crack spread) from live futures prices. Use when asked about energy prices, oil markets, gas markets, or for a market brief / morning note.
---

# Energy Market Brief

## Steps

1. Run the `scripts/fetch_prices.py` script to get live futures data. Pass one
   argument with the lookback range: `5d`, `1mo` (default), `3mo`, `6mo` or `1y`.
2. Use only the numbers returned by the script. Never invent prices. If a contract
   returns an `error`, say the data was unavailable.
3. If the `energy-news-digest` skill is available, use it too so you can explain
   *why* prices moved.
4. Write the brief in the format below.

## Brief format (Markdown)
   # Energy Market Brief: <date>
   **Bottom line:** ...
   ## Prices  | Contract | Latest | 1-day | Period | Range |
   ## What moved the market
   ## Signals to watch
   ## So what for an energy company

The second skill, energy-news-digest, runs scripts/fetch_news.py [topic] [max] against public RSS feeds (OilPrice.com, EIA, Google News) and groups headlines into bullish, bearish or neutral themes. Step 3 above shows how skills compose: the brief skill tells the model to pull in the news skill when it is available.

Design split
The model does judgment: choosing skills, interpreting moves, writing prose. The script does facts: fetching data and computing spreads. That split is what makes "never invent numbers" enforceable. Scripts use only the standard library, take positional string arguments, print JSON, report per-item errors and finish within the runner's 30-second timeout.
Gotcha
Front matter values must be unquoted and free of colons, and name must match the folder name, or the Foundry upload in Part B fails validation.

Script runner subprocess_script_runner.py

FileSkillsSource doesn't run scripts itself. It delegates to a script_runner callback you supply. This sample runs each script in a child Python process:

subprocess_script_runner.pydef subprocess_script_runner(skill: FileSkill, script: FileSkillScript, args=None) -> str:
    script_path = Path(script.full_path)
    if not script_path.is_file():
        return f"Error: Script file not found: {script_path}"
    cmd = [sys.executable, str(script_path)]        # same interpreter as the agent
    if isinstance(args, list):
        for item in args:
            if not isinstance(item, str):
                raise TypeError("File-based skill scripts only accept string CLI arguments ...")
        cmd.extend(args)
    elif args is not None:
        raise TypeError("Expected a list of CLI arguments ...")
    try:
        result = subprocess.run(cmd, capture_output=True, text=True, timeout=30,
                                cwd=str(script_path.parent))
        output = result.stdout
        if result.stderr:
            output += f"\nStderr:\n{result.stderr}"
        if result.returncode != 0:
            output += f"\nScript exited with code {result.returncode}"
        return output.strip() or "(no output)"
    except subprocess.TimeoutExpired:
        return f"Error: Script '{script.name}' timed out after 30 seconds."
  • Process isolation: a script can't mutate the agent's Python state.
  • Errors become text, so the model can see a failure and react instead of crashing the turn.
  • Not a sandbox: the child inherits the agent's environment and credentials. See Before production.

  • Bounded startup: a 45-second timeout keeps a slow preview API from hanging the container.
  • Graceful degradation: if download fails, the skills baked into the image are used, so the agent stays healthy.
  • Defensive extraction: archives are external input, so paths escaping the target folder are rejected.
  • Placeholder-safe env: an unresolved ${SKILL_NAMES} is treated as empty instead of crashing.

Dockerfile

A slim Python image that installs requirements.txt, exposes 8088 and precompiles bytecode (stdlib, dependencies and app) so cold starts are faster. Entry point: python main.py.

RBAC

The hosted agent's managed identity needs the Foundry User role on the Foundry account to download skills. make deploy calls make rbac, which looks up the agent's instance identity with azd ai agent show and assigns the role idempotently.

Silent failure mode
Without the role, skill download fails and the agent quietly uses its baked-in skills. It still works, which hides the problem. Always check the logs (next section).

Before production

This repo is a demo. These are deliberate shortcuts to call out:

  • Approvals are off. Re-enable skill load, script and resource approvals, and harness auto-approval rules, for anything with side effects.
  • The script runner is not a sandbox. Consider an allow-list, resource limits, a separate identity and scrubbing secrets from output.
  • Skill supply chain. Anyone who can publish to the project's skills store changes the agent's behavior at its next start. Restrict write access and consider pinning versions.
  • No evaluations, tracing or tests. Add evaluation datasets, telemetry, script unit tests and a make demo-2 smoke test in CI.
  • Public, delayed data. Replace with licensed or internal sources, authenticated through managed identity or Key Vault. The output is not investment advice.

Exercises

  1. Trim the harness. In Demo 1, add disable_todo=True, disable_mode=True, disable_web_search=True. What changes in answers and latency? When would you go further and use Agent directly?
  2. Re-enable web search in build_energy_agent via an override and compare a brief with and without it. Which numbers can you still trace to tool output?
  3. Write a third skill, for example rig-count or eia-storage: a SKILL.md with a "Use when ..." description and a stdlib script that prints JSON. Run make demo-2 and watch whether the model picks it up.
  4. Change the brief format only by editing energy-market-brief/SKILL.md, then run make skills and make invoke. No redeploy needed.
  5. Break RBAC on purpose (or set a bad SKILL_NAMES), redeploy, and find the fallback message in make logs.
  6. Adapt the repo to your own domain by following docs/BUILD_YOUR_OWN_AGENT.md.
